# ТЗ: автоматический сбор объявлений из чатов без добавления бота

**Проект:** `Bergaff/parcel` — доска попутных передач «попутка.» (Cloudflare Pages + Workers + D1 + KV, Telegram-бот на Hono).
**Дата ТЗ:** 2026-09-15. **Ветка для работы:** своя, от `main`.
**Исполнитель:** отдельный (серверная часть — в этом репозитории; браузерное расширение — на стороне исполнителя, но контракт API обязателен к соблюдению).

---

## 0. Суть задачи

Сейчас объявления попадают на доску двумя путями: (1) бот добавлен в чат и видит сообщения в реальном времени, (2) человек пересылает сообщение боту в личку. Оба требуют либо добавления бота в чат, либо ручной работы.

Нужно **два новых источника**, которые работают без добавления бота в чаты:

- **Вариант A — серверный сборщик публичных чатов.** Cron в воркере раз в 1–2 часа читает веб-превью публичных каналов/супергрупп `https://t.me/s/<username>` (открывается без логина), забирает новые сообщения и прогоняет их через существующий конвейер разбора.
- **Вариант B — приём сообщений из браузерного расширения.** Расширение/юзерскрипт работает в открытой вкладке Telegram Web **на аккаунте заказчика** (только чтение), детектит сообщения по словам и отправляет текст в новый эндпоинт воркера `POST /api/ingest`. Пересылка через Telegram не используется.

Оба варианта обязаны выходить в **существующую очередь модерации** (`status = 'pending'`, уведомление админам) и **не дублировать** уже обработанные сообщения.

### Цели
1. Убрать ручной труд: «раз в час посмотреть чаты и переслать».
2. Исключить необходимость помнить «до какого времени я уже просмотрел» — курсор хранится на сервере.
3. Не менять существующий разбор: правила → ИИ → модерация, те же карточки.

### Не делать (non-goals)
- ❌ Юзерботы на MTProto (Telethon/Pyrogram/GramJS), покупные аккаунты, вход в аккаунт с сервера/датацентра.
- ❌ Любые **записывающие** действия от имени аккаунта заказчика (постинг, ответы, массовые пересылки, реакции). Только чтение.
- ❌ Публикация собранных объявлений без модерации (даже при `AUTO_APPROVE=1`).
- ❌ Сбор из приватных чатов на сервере (приватные чаты — только вариант B, из браузера заказчика).
- ❌ Переписывание парсера/ИИ под новые источники: конвейер один на всех.

## 2. Общая часть (делать до обоих вариантов)

### 2.1 Вынести конвейер в `src/ingest.ts`
Создать модуль `src/ingest.ts`, перенести туда из `src/telegram.ts` (без изменения поведения):

```
export interface IngestSource {
  chatId: string;        // ключ чата для tg_seen / source_chat_id
  chatTitle: string | null;
  messageId: number | null;
  chatUrl?: string | null;   // публичная ссылка на чат (t.me/<username>)
  authorName?: string | null;
  authorUsername?: string | null;
  origin: 'bot' | 'collector' | 'extension';
}

export interface IngestResult {
  status: 'created' | 'duplicate' | 'skipped' | 'invalid';
  reason?: 'passenger' | 'no_intent' | 'ai_empty' | 'too_old' | 'too_long' | 'bad_payload';
  listings: Listing[];       // созданные заявки (0..3)
  existingListingId?: string | null; // для duplicate — что уже было создано
}

export function cascade(env, text): Promise<{ list: AiFields[]; source: 'telegram' | 'parser' }>
export async function ingestMessage(env, text: string, src: IngestSource, opts?: { maxAgeDays?: number; useAi?: boolean }): Promise<IngestResult>
```

Порядок операций внутри `ingestMessage()` — **строго такой**:
1. `text` пустой или > 4000 символов → `invalid` / `skipped:too_long`.
2. Сообщение старше `maxAgeDays` (если дата передана) → `skipped:too_old`.
3. `isPassengerOnly(text)` → `skipped:passenger`.
4. `markSeen(env, src.chatId, src.messageId)` вернул `false` → `duplicate`, дополнительно вернуть `getSeenListing()` как `existingListingId`. **Это единственная защита от дублей — она должна выполняться до любых вызовов ИИ.**
5. `cascade(env, text)` (при `useAi === false` — только правила). Пустой список → `skipped` (`ai_empty` или `no_intent`), при этом запись в `tg_seen` **оставить** (повторно не обрабатываем).
6. Для каждого элемента: `createListing()` c `status='pending'`, `source` из `cascade`, `source_chat = src.chatTitle`, `source_chat_id = src.chatId`, `source_message_id = src.messageId`, `origin = src.origin`; затем `setSeenListing()` (для первой созданной заявки).
7. `notifyAdmins()` на каждую созданную заявку.
8. Ошибка создания → откатить `tg_seen` (удалить строку), как это сделано сейчас в `handleGroupText()`.

`src/telegram.ts` после этого вызывает `ingestMessage()`/`cascade()` из нового модуля; поведение бота не меняется, все существующие тесты должны остаться зелёными.

### 2.2 Миграция `0004_ingest.sql`
```sql

  title          TEXT,
```

### 2.3 Ссылка на исходное сообщение
`listingSourceLink(sourceChatId, sourceMessageId)` в `src/telegram.ts` сейчас умеет только `-100<id>` → `https://t.me/c/<id>/<msg>`. Расширить:
- `web:<username>` + messageId → `https://t.me/<username>/<messageId>`;
- `web:<username>` без messageId → `https://t.me/<username>`;
- `ext:*` (приватные чаты из расширения) → `null`, если в `chat_links` не задана ссылка вручную;
- приоритет остаётся у `chat_links` (как сейчас на сайте: `sourceLinkUrl()` в `public/app.js`).

### 2.4 Что нужно починить в существующем коде
- `listSourceChats()` в `src/store.ts` фильтрует `source_chat_id LIKE '-%'` — новые ключи (`web:*`, `ext:*`) не попадут на вкладку «чаты». Расширить условие до `LIKE '-%' OR source_chat_id LIKE 'web:%' OR source_chat_id LIKE 'ext:%'`.
- `scheduled()` в `src/index.ts` игнорирует `event.cron`. С появлением второго триггера обязателен `switch (event.cron)`, иначе архивация будет запускаться вместе со сборщиком.
- Квота ИИ: `aiQuotaOk()` в `src/ai.ts` тратит общий дневной лимит 300. Для авто-сбора нужен **отдельный** счётчик (см. 3.5 и 4.4), чтобы сборщик не съедал бюджет бота.

## 3. Вариант A — серверный сборщик публичных чатов

### 3.1 Архитектура
Новый файл `src/collect.ts`:
```
export async function collectPublicChats(env, opts?: { onlyChatId?: string; dryRun?: boolean }): Promise<CollectReport>
export async function fetchPreview(username: string, before?: number): Promise<PreviewPage>   // чистая часть — fetch
export function parsePreviewHtml(html: string): PreviewMessage[]                              // чистая функция, тестируется на фикстурах
```
Запуск: `scheduled()` (ветка по `event.cron`) и вручную `POST /api/admin/collect` (см. 3.6).

### 3.2 Источник данных
- `GET https://t.me/s/<username>` — веб-превью публичного канала, **без авторизации** (проверено на `t.me/s/durov`).
- Пагинация вглубь истории: `GET https://t.me/s/<username>?before=<message_id>`.
- Для публичных **супергрупп** превью обычно тоже доступно, но это надо проверить для каждого конкретного чата до добавления в список (см. 3.7, поле `kind`).
- Ответ — HTML. Парсить через **`HTMLRewriter`** (доступен в Workers) или аккуратными регулярками; `DOMParser` в Workers нет.

### 3.3 Что извлекаем из каждого сообщения (`PreviewMessage`)
| Поле | Откуда | Обязательно |
|---|---|---|
| `messageId: number` | атрибут `data-post="<username>/<id>"` у контейнера сообщения; **подтверждённый запасной вариант** — permalink `href="https://t.me/<username>/<id>"` (присутствует в выдаче, проверено) | да |
| `text: string` | текстовый блок сообщения (исторически `.tgme_widget_message_text`), `<br>` → `\n`, теги и `VIEW IN TELEGRAM`-обвязку выбросить, emoji/сущности оставить как есть | да |
| `date: string (ISO)` | `<time datetime="...">` в мете сообщения; запасной вариант — видимая дата/время («May 10», «14:42») | да |
| `author: string \| null` | имя автора/канала в подписи | нет |
| `hasMedia: boolean` | наличие медиа-блока | нет |

Точные имена классов/атрибутов **сверить на живой разметке до написания парсера** ( curl `https://t.me/s/<username>` и `https://t.me/s/<username>?before=<id>` ); в коде не хардкодить один признак — брать `messageId` из двух источников (атрибут, затем permalink), чтобы смена вёрстки не обнуляла сбор.

Требования к парсеру: не падать на неизвестной разметке; сообщение без `messageId` или без `text` — пропускать; текст собирать с переносами строк (`\n`), а не в одну строку; максимальная длина — 4000 символов (дальше обрезка, как в боте).

### 3.4 Алгоритм одного запуска
1. `COLLECT_ENABLED !== '1'` → выйти (лог).
2. Проверить дневной счётчик ИИ сборщика (KV `ai:collect:day:<YYYY-MM-DD>`); если превышен — собирать **только правилами** (`useAi: false`).
3. Взять из `watch_chats` включённые чаты, упорядочить по `last_checked_at ASC NULLS FIRST`, ограничить `COLLECT_MAX_CHATS`. Ротация обязательна: за один запуск обходим не все чаты, а порцию (лимит подзапросов на вызов — на бесплатном тарифе ~50).
4. Для каждого чата:
   a. `fetchPreview(username)` (первая страница).
   b. Отфильтровать сообщения с `messageId <= last_message_id` (курсор) и старше `COLLECT_MAX_AGE_DAYS`.
   c. Если новых сообщений больше, чем влезло на страницу, и `last_message_id` неизвестен (первый запуск) — **не** листать глубоко: взять только первую страницу и поставить курсор на максимум (иначе при первом включении зальём год истории).
   d. Обработать сообщения **по возрастанию id**, каждое через `ingestMessage(env, text, { chatId: 'web:'+username, chatTitle: title ?? username, messageId, chatUrl: 'https://t.me/'+username, origin: 'collector' }, { maxAgeDays, useAi })`.
   e. Продвинуть курсор `last_message_id = max(обработанные id)`, обновить `last_checked_at`, счётчики `stats_*`, сбросить `error_count`.
   f. Нужна ли вторая страница (`COLLECT_MAX_PAGES`) — только если на первой все сообщения оказались новыми и их число равно размеру страницы.
5. Между запросами к разным чатам — небольшая пауза (порядка 200–500 мс) и строгий лимит общего числа подзапросов за вызов. Никаких параллельных `Promise.all` на десятки чатов.
6. Вернуть/залогировать `CollectReport`: по каждому чату `{ chatId, fetched, new, created, skipped, duplicate, cursorBefore, cursorAfter, error? }` + итоги.

**Идемпотентность:** даже при сбое курсора повторный обход не создаст дублей — `markSeen()` в `tg_seen` отсеет уже обработанное. Курсор — оптимизация, а не защита от дублей.

### 3.5 Квота ИИ
- Свой счётчик: KV `ai:collect:day:<дата>` (TTL 2 суток), лимит `COLLECT_AI_DAILY_LIMIT`.
- Перед вызовом ИИ для сообщения сборщик проверяет и инкрементирует **свой** счётчик, общий (`ai:day:*`) остаётся для бота.
- Дополнительно: перед ИИ обязательно `worthAiCheck(text)` (уже есть в `cascade`) — болтовня не должна тратить квоту.

### 3.6 Админ-API
Все роуты под существующим middleware `/api/admin/*` (Bearer `ADMIN_API_TOKEN`).

| Метод и путь | Назначение |
|---|---|
| `GET /api/admin/watch-chats` | список с курсорами, счётчиками, ошибками |
| `POST /api/admin/watch-chats` | добавить `{ username, kind?, title? }` → создаёт `id = 'web:'+username`; 409 если уже есть |
| `PUT /api/admin/watch-chats/:id` | правка `{ enabled?, kind?, title?, last_message_id? }` (сброс курсора — осознанное действие) |
| `DELETE /api/admin/watch-chats/:id` | удалить из обхода (заявки не трогаем) |
| `POST /api/admin/collect` | ручной прогон; body `{ chatId?, dryRun? }`; `dryRun: true` — только чтение и отчёт, без `createListing` и без движения курсора |
| `GET /api/admin/collect/status` | последний отчёт (хранить в KV `collect:last-report`, TTL 7 дней) + суммарные счётчики |

При добавлении чата — сразу записать в `chat_links` строку `web:<username>` → `https://t.me/<username>` (через существующий `upsertChatLink`), чтобы на сайте источник был кликабельным.

### 3.7 Обработка ошибок и деградация
- HTTP ≠ 200, пустой ответ, таймаут → не двигать курсор, `last_error`, `error_count++`.
- Разметка изменилась (страница 200, но `parsePreviewHtml` вернул 0 сообщений, хотя раньше возвращал) → `error_count++`, `last_error = 'markup_changed?'`.
- `error_count >= 3` → автоматически `enabled = 0` и уведомление админам в Telegram (текст: «Сборщик остановлен по чату <username>: <last_error>. Проверьте разметку t.me/s/»).
- «Мёртвый» чат (удалён/переименован, 404) → `enabled = 0` сразу.
- Никаких повторных попыток в том же запуске: ошибка чата не должна ронять весь прогон.

### 3.8 UI (вкладка «чаты» в `public/app.js`)
Добавить к существующему списку источников блок «Авто-сбор публичных чатов»:
- таблица: username, тип, вкл/выкл, курсор (`last_message_id`), последняя проверка, найдено/создано/отсеяно, последняя ошибка;
- форма добавления (username + тип), кнопки «выключить/включить», «сбросить курсор», «проверить сейчас» (вызывает `POST /api/admin/collect` с `chatId`);
- кнопка «Отчёт последнего прогона» → `GET /api/admin/collect/status`, показать JSON в читаемом виде;
- в карточках очереди модерации показать `origin` («сборщик» / «расширение» / «бот») — рядом с существующей подписью источника.

## 4. Вариант B — `POST /api/ingest` для браузерного расширения

### 4.1 Архитектура
Новый роут в `src/index.ts` (вне `/api/admin/*`, своя авторизация) + переиспользование `ingestMessage()` из `src/ingest.ts`. Сервер **ничего не знает о браузере**: он принимает текст и метаданные, всё остальное делает существующий конвейер.

### 4.2 Авторизация и CORS
- `Authorization: Bearer <INGEST_TOKEN>`; `INGEST_TOKEN` — отдельный секрет (не `ADMIN_API_TOKEN`), чтобы можно было отозвать, не теряя админ-доступ. При отсутствии секрета в env → 503 (фича выключена).
- Запросы приходят с origin `https://web.telegram.org` → существующий CORS-middleware на `/api/*` уже отдаёт `Access-Control-Allow-Origin: <origin>`, методы `GET, POST, OPTIONS` и заголовки `Content-Type, Authorization`, плюс `OPTIONS` → 204. Проверить, что `PUT` не нужен; если нужен — добавить в список методов.
- Rate limit через существующий `rateLimit(env, key, max, windowSec)`: `ingest:<первые 8 символов токена>` — 60 запросов/час; при превышении → 429 с `Retry-After`.
- Максимум 100 сообщений в одном запросе → иначе 413/400.

### 4.3 Контракт

**Запрос**
```json
POST /api/ingest
Authorization: Bearer <INGEST_TOKEN>
Content-Type: application/json

{
  "collector": "tg-web-ext/1.0.0",
  "dryRun": false,
  "messages": [
    {
      "chatId": "web:drivers_pl_by",
      "chatTitle": "Водители Польша–Беларусь",
      "chatUrl": "https://t.me/drivers_pl_by",
      "messageId": 12345,
      "date": 1789000000,
      "text": "Варшава — Брест, возьму посылку до 20 кг, +48 579 264 254",
      "authorName": "Adelina Yasiuchenia",
      "authorUsername": "@adelina_y"
    }
  ]
}
```

| Поле | Тип | Обяз. | Правило |
|---|---|---|---|
| `messages` | array 1..100 | да | |
| `messages[].chatId` | string 1..64 | да | стабильный ключ чата. Публичный: `web:<username>`. Приватный: `ext:<внутренний id чата>` (числовой id из клиента). Используется для `tg_seen` и `source_chat_id` |
| `messages[].messageId` | integer > 0 | да | id сообщения в этом чате |
| `messages[].text` | string 1..4000 | да | текст как есть, с переносами |
| `messages[].chatTitle` | string ≤ 120 | нет | попадёт в `source_chat` |
| `messages[].chatUrl` | string ≤ 200 | нет | публичная ссылка на чат; при наличии — сохраняется в `chat_links` |
| `messages[].date` | unix seconds **или** ISO-строка | нет | для отсева старых (`maxAgeDays = 3` для варианта B) |
| `messages[].authorName` | string ≤ 120 | нет | для подписи источника |
| `messages[].authorUsername` | string ≤ 64 | нет | если задан и в сообщении нет контакта — станет `telegram` заявки (как сейчас у пересылок: контакт — автор сообщения) |
| `dryRun` | boolean | нет | `true` — разобрать и вернуть результат, **не** создавая заявок и **не** трогая `tg_seen` |
| `collector` | string ≤ 64 | нет | версия клиента, уходит в лог |

**Ответ 200**
```json
{
  "ok": true,
  "summary": { "received": 3, "created": 1, "duplicate": 1, "skipped": 1, "invalid": 0 },
  "results": [
    { "messageId": 12345, "status": "created",
      "listings": [{ "id": "6336…", "type": "offer", "fromCity": "Варшава", "toCity": "Брест", "departureDate": null }] },
    { "messageId": 12340, "status": "duplicate", "listingId": "a1b2…" },
    { "messageId": 12341, "status": "skipped", "reason": "passenger" }
  ],
  "cursors": { "web:drivers_pl_by": 12345 }
}
```
`cursors` — максимальный принятый `messageId` по каждому `chatId` из запроса. Клиент **может** использовать его как локальный курсор, но обязан присылать с перекрытием: источник истины — сервер (`tg_seen`).

**Ошибки:** `400` (битое тело, не тот тип полей), `401` (нет/неверный токен), `413` (>100 сообщений), `429` (лимит), `503` (`INGEST_TOKEN` не задан). Тело ошибки — `{ "error": "..." }`, как в остальных роутах.

### 4.4 Логика обработки на сервере
1. Валидация тела и каждого сообщения (невалидные — в `results` со `status: 'invalid'`, остальные обрабатываются).
2. `rateLimit`.
3. Для каждого сообщения — `ingestMessage()` с `origin: 'extension'`, `chatId` как пришёл, `source = 'parser' | 'telegram'` из `cascade`.
4. Заявки **всегда** `status = 'pending'` (игнорировать `AUTO_APPROVE`), `notifyAdmins()` на каждую.
5. `useAi`: по умолчанию `true`, но с собственным счётчиком квоты `ai:ingest:day:<дата>` (лимит — `COLLECT_AI_DAILY_LIMIT`, общий с вариант A или отдельный — на усмотрение исполнителя, но **не** общий с ботом).
6. `dryRun: true` — прогнать шаги 3–4 в режиме «только разбор»: вернуть `parseTelegramMessage()` + (опционально) результат ИИ, ничего не писать в БД. Используется расширением для предпросмотра «найдено N кандидатов».
7. Порядок обработки — по возрастанию `messageId` внутри каждого `chatId`.

### 4.5 Требования к расширению (контракт поведения, реализация — на стороне исполнителя)
- Работает в вкладке `https://web.telegram.org` **на аккаунте заказчика**; только чтение DOM. Никаких отправок сообщений, кликов по чужим чатам, реакций, пересылок.
- Белый список чатов задаётся пользователем в настройках расширения (по названию/ссылке); всё остальное игнорируется полностью.
- Опрос раз в 60–180 с (настраиваемо), порционно: не более ~20 сообщений за один `POST /api/ingest`.
- **Первичный детект на клиенте** — чтобы не отправлять на сервер весь поток: переиспользовать `src/parser.ts` (модуль чистый, собирается бандлером) — `isPassengerOnly()` отсевает пассажирские, `worthAiCheck()` — болтовню, `parseTelegramMessage()` даёт маршрут/тип для подсветки. Допустим и более простой локальный список ключевых слов, но тогда серверный `dryRun` обязателен для предпросмотра.
- Перекрытие окон: каждый проход брать последние N сообщений чата (например 30) и отправлять всё, что не отмечено локально как отправленное; дубли отсеет сервер (`status: 'duplicate'`) — это штатный режим, не ошибка.
- UI: счётчик «найдено / отправлено / дубли», кнопка «Пауза», кнопка «Отправить все найденные» и режим «спрашивать подтверждение» (по умолчанию — включён).
- Хранение: `INGEST_TOKEN` и настройки — в `chrome.storage`/`localStorage`, в коде репозитория токена быть не должно.
- Устойчивость: при `401/503` — остановиться и показать ошибку; при `429` — backoff; при смене разметки Telegram Web — показать «не могу прочитать сообщения», а не молча работать.
- Логирование на сервер не отправлять (кроме поля `collector`).

### 4.6 Что добавляется на сайт для варианта B
- В админ-панели: статус «расширение» — сколько принято сообщений/создано заявок за сутки (можно из `listings.origin = 'extension'`), плюс инструкция, где взять токен (`wrangler secret put INGEST_TOKEN`).
- Фильтр очереди модерации по `origin` (бот / сборщик / расширение).

## 6. Критерии приёмки

**Общие**
1. Повторная обработка одного и того же сообщения (любым из трёх источников) не создаёт вторую заявку — возвращает `duplicate` и существующий id.
2. Все собранные заявки попадают в `pending` и уведомляют админов; `AUTO_APPROVE=1` на них не влияет.
3. В карточке модератора и на сайте виден источник: название чата + кликабельная ссылка на исходное сообщение (для публичных чатов), а также признак `origin`.
4. Дневной лимит ИИ бота (300) не расходуется авто-сбором; у сборщика/расширения свой счётчик, при его исчерпании разбор продолжается правилами.
5. `npm test` и `npm run typecheck` зелёные; миграция `0004` применяется `npm run deploy` без ручной правки базы.

**Вариант A**
6. Добавление публичного канала через админку → за один-два прогона новые сообщения превращаются в заявки, курсор двигается, отчёт виден в UI.
7. Прогон не превышает лимит подзапросов воркера (ротация чатов по `COLLECT_MAX_CHATS`), при ошибке чата остальные обрабатываются.
8. После 3 ошибок подряд чат выключается сам, админы получают сообщение в Telegram.
9. При первом включении чата история назад не выкачивается (берётся только первая страница).

**Вариант B**
10. `curl` с токеном и батчем из 3 сообщений (одно — дубль, одно — пассажирское, одно — объявление) даёт ожидаемый `summary` и одну созданную заявку.
11. `dryRun: true` не создаёт заявок и не помечает сообщения обработанными (последующий обычный запрос создаёт заявку).
12. Запрос с origin `https://web.telegram.org` из браузера проходит CORS, включая preflight.
13. 61-й запрос за час → `429`.

## 8. Риски и как их снижаем

| Риск | Вероятность | Митигция |
|---|---|---|
| Telegram изменит разметку `t.me/s/` → парсер сломается | средняя | чистая функция `parsePreviewHtml` + фикстуры; авто-отключение чата после 3 ошибок и алерт админам; не двигать курсор при ошибке |
| Telegram начнёт блокировать/рейт-лимитить запросы с IP Cloudflare | средняя | редкий обход (раз в 1–2 ч), ротация чатов, паузы между запросами, `User-Agent` как у браузера, при 429 — увеличивать интервал |
| Публичная супергруппа не имеет веб-превью | средняя | проверять до добавления; поле `kind`; при 0 сообщений — не включать |
| Блокировка/ограничение аккаунта заказчика за автоматизацию Telegram Web | низкая–средняя | только чтение, свой бытовой IP, официальный клиент, редкий опрос, режим «спрашивать подтверждение», отдельный (не основной) номер, никаких массовых действий |
| Расширение начнёт отправлять мусор → завалит очередь модерации и квоту ИИ | средняя | клиентский детект (`worthAiCheck`, `isPassengerOnly`), серверный `dryRun`, лимиты батча и rate limit, отдельные счётчики ИИ |
| Дубли при перекрытии окон | высокая (по дизайну) | `tg_seen` как единственный источник истины; `duplicate` — штатный ответ |
| Личные данные (номера телефонов) уходят на сервер из приватных чатов | высокая | отправляются только сообщения, прошедшие детект; всё через модерацию; на сайте контакт показывается так же, как сегодня у пересланных заявок; правило «не публикуем без одобрения» сохраняется |
| Лимиты воркера (cron 3–5 на Worker, ~50 подзапросов на вызов на free) | средняя | один новый cron (итого 2), ротация чатов, батчинг; при росте — вынести сборщик в отдельный Worker |
| Квота ИИ (300/день) съедается авто-сбором | высокая без защиты | отдельные счётчики `ai:collect:day:*` / `ai:ingest:day:*`, дефолт 100, при превышении — разбор только правилами |

## 10. Справка для исполнителя

Пример того, что должно получиться на выходе (карточка модератора, существующий формат `formatListing`):
```
#63367269 Водитель везёт
Маршрут: Варшава → Минск
Дата: 2026-09-25
Описание: Возьму посылки, домашние переезды. Telegram, Whatsapp.
Контакты: +48579264254
Источник: ИИ-разбор, чат «Водители Польша–Беларусь» — исходное сообщение
```
Требования к ней уже реализованы и не должны сломаться: контакты без дублей (`normalizeContacts`/`uniqueContacts`), описание не повторяет поля карточки (`dedupeDescription`), тип заявки определяется по сильным признакам (`scoreIntent`), спорные случаи уходят ИИ (`confidence < 0.7`).

Проверка веб-превью без логина (повторить руками перед разработкой парсера):
```
curl -s -A 'Mozilla/5.0' 'https://t.me/s/durov' -o page.html
grep -o 'https://t.me/durov/[0-9]*' page.html | sort -u | tail -5   # id сообщений есть
curl -s -A 'Mozilla/5.0' 'https://t.me/s/durov?before=528' -o older.html   # пагинация вглубь
```
Подтверждено на момент написания ТЗ: страница отдаётся без авторизации, id сообщений видны в permalink'ах, `?before=<id>` возвращает более старые сообщения. Имена CSS-классов и атрибут `data-post` — сверить на живой разметке (см. 3.3).

Команды проекта: `npm install`, `npm test`, `npm run typecheck`, `npm run dev`, `npm run db:local`, `npm run deploy` (применяет миграции D1 и деплоит воркер).
